# 一张真实体检单怎么用

> 2026-10-17　针对《检后有伴》当前状态（字典 41 条、12 份合成样本、零真实样本）

---

## 零、先纠正一个前提：你的项目里没有"训练"

《检后有伴》的技术底座是 **OCR + 指标字典 + 本地规则引擎**，不是机器学习模型。
没有任何东西需要"训练"——这也正是架构铁律「数字绝不来自大模型」能成立的原因。

所以"拿去训练"要翻译成三件具体的事：

| 你想说的 | 实际该做的 |
|---|---|
| 训练识别能力 | **校准字典**：把真实报告上印的指标名/别名/单位/区间补进 `markers.json` |
| 训练解析能力 | **校准解析器**：让 `ocr/parser.py` 认识真实报告的版式和区间写法 |
| 训练判定能力 | **校准红线**：用真实异常值验证 `rules/engine.py` 判定方向对不对 |

这三件事的本质是**人工校准规则**，不是喂数据给模型。别走岔路（见第四章）。

---

## 一、一张够不够：分用途回答

| 用途 | 一张够吗 | 说明 |
|---|---|---|
| 证明"真实报告能跑通" | **够（及格线）** | 但只覆盖一种版式，结论很脆 |
| 建立 OCR 评测集 | **不够**（统计上无意义） | 1 个样本算不出可信的准确率 |
| 扩充指标字典 41 → 120 | **能解决一半** | 一份报告通常 20-30 个指标，能补到 60-70 |
| 发现解析器的隐含 bug | **够，而且这是它最值钱的地方** | 见第二章 |
| 当演示视频素材 | **够** | 且能让 README 里"数据来自真实场景"这句成立 |

**结论：一张够用来「证伪」，不够用来「证明」。而证伪才是你最需要的。**

---

## 二、它真正的价值：打破你现在的自证循环

现在 12 份合成样本 100% 命中，但这个数字是**假的**——合成报告是你按 `parser.py` 的假设画出来的，它天然契合你的解析器。你等于自己出题自己考自己。

真实报告的唯一价值就是**打破这个循环**：它上面有你没预料到的写法。

预期会被打脸的几处（照着重点看）：

- 指标名印刷形式：`总胆固醇(TC)` / `总胆固醇 TC` / `TC` / `CHOL`
- 参考区间写法：`3.10-5.20` / `3.10~5.20` / `<5.20` / `0-40` / `阴性(-)`
- 单位：`×10⁹/L` 被 OCR 认成什么鬼样子（合成件里你已经登记了 `unit_ocr_variants`，真实件会有新形态）
- 箭头符号位置：`↑` 在数值前 / 后 / 单独一列
- 合并单元格、一个格子塞两行

**如果这一张能让你的解析器崩 3 处，它比 10 张合成报告都值钱。**

## 三、执行步骤（半天能做完）

### Step 0 · 脱敏（不能省）

抹掉：姓名 / 身份证号 / 体检号 / 医院名 / 医生名 / 二维码条形码。
最省事的做法：**只截取"检验结果表格"那一块**，表头信息整段不要。

> `samples/` 已被 gitignore，但 `expected/*.json` **会**进公开仓库——
> 标注里绝对不能出现任何身份信息。

### Step 1 · 标注 ground truth

放 `samples/real_001.jpg`，然后建 `expected/real_001.json`：

```json
{
  "source": "真实拍照件，某三甲医院，单栏有框线表",
  "markers": [
    { "name": "尿酸", "value": "512", "unit": "μmol/L", "ref": "208-428" }
  ]
}
```

挑 **20 个左右**就够，照报告逐字抄。`ref` 印的是 `208~428` 就写 `208~428`，别规范化——
解析器该适应报告，不是报告适应解析器。

### Step 2 · 跑评测

```bash
D:/aconda3/envs/hwh_ml/python.exe tests/ocr_bench/bench.py --provider rapidocr
```

**重点看 `ref` 那一列**（参考区间）——区间判错，红线就判错，整套逻辑全歪。

### Step 3 · 失败归因（照这张表分类）

| 失败类型 | 现象 | 该改哪 |
|---|---|---|
| A. OCR 没认出来 | 原始文本里根本没有这一行 | 换 provider / 前端加"正对拍摄"引导 |
| B. 认出来了但切错行 | 文本对，四元组错 | 改 `ocr/parser.py` |
| C. 字典里没这条 | 名字抽对了但匹配不上 | 补 `markers.json` 的 `aliases` |
| D. 单位不匹配 | 值对、单位形态新 | 补 `unit_ocr_variants` |
| E. 区间格式新 | `<5.20`、`阴性(-)` 之类 | 改 `parser.py` 的区间解析 |

### Step 4 · 变体扩增（**一张变十张的唯一合法办法**）

真实版式千差万别，你只有一张，覆盖不了。但**同一张的退化变体**能免费测鲁棒性，
而且 ground truth 可以直接复用（内容没变，只是变糊了）：

```python
# tests/ocr_bench/augment.py（我可以直接帮你建）
# 对 real_001.jpg 施加：旋转 ±3°/±6°、高斯模糊、单侧明暗、JPEG 压缩、
# 椒盐噪点、透视倾斜、局部阴影（模拟手指遮挡）
# → 产出 real_001_a.jpg ... real_001_g.jpg，expected 全部复用 real_001.json
```

跑完你会得到一条**鲁棒性曲线**：清晰件多少分、旋转 6° 多少分、压缩后多少分。
这条曲线比一个孤零零的准确率数字有说服力得多——它直接对应 README 里
"拍照件风险"那条已知限制，也支撑了"前端要加拍摄引导"这个设计决策。

### Step 5 · 校准三件套，然后回归

改完字典/解析器后重跑全量：合成 12 份 + 真实 1 份 + 变体 7 份，
确保 319 条断言没被改坏。

### Step 6 · 写进 README

在「已知限制」和「评审证据索引」里新增一小节 **真实场景验证**：
写明真实样本数（1 份 + 7 变体）、命中率、发现的 3 个问题与修复方式。
**如实写 1 份，比不写强；如实写 1 份 + 说清局限，比吹成 10 份强。**

## 四、绝对不要做的事

**别去"训练一个模型"。** 四个理由：

1. **赛道不考这个**——Vibe Coding 赛道 60% 分数不靠硬核技术，Agent/RAG 深度那是隔壁 10040 赛道的事。
2. **数据不够**——几十张训不出可用的 OCR，这是工业级问题。
3. **自相矛盾**——你的架构铁律是"数字绝不来自大模型、判定全在本地"，走"训练"路线会把你最独特的卖点稀释掉。
4. **时间不够**——距提交 32 天，演示视频和字典扩充都还没做。

你的护城河是**规则的可解释性 + 数值级反幻觉**，不是模型精度。别把长板换成短板。

## 五、时间预算

| 步骤 | 耗时 |
|---|---|
| 脱敏 + 标注 20 个指标 | 30 分钟 |
| 跑 bench + 归因 | 1 小时 |
| 补字典 / 改解析器 | 1-2 小时 |
| 变体扩增 + 重跑 | 1 小时 |
| 写进 README | 20 分钟 |

**合计半天。** 这是目前性价比最高的一件事——它把你从"自证循环"里捞出来，
也是评委最容易追问的那个点上唯一能给出诚实答案的办法。

## 六、如果你能拿到更多

优先级排序（每多一份，边际收益递减）：

1. **第 2 份：不同医院**（版式差异最大，暴露的解析器问题最多）
2. **第 3 份：PDF 电子版**（清晰件上限，用来证明"清晰件没问题，问题只在拍照质量"）
3. 第 4 份及以后：收益已经很小，不必强求

**底线：1 份真实 + 7 个变体 + 12 份合成，如实写进文档，对比赛已经足够。**

# 第一章 · 意图控制策略

> 本章描述《检后有伴》如何把「大模型能做什么、不能做什么」写成代码约束，
> 而不是写成一句 prompt 里的请求。
>
> **证据基线**：代码以提交 `91e8b0c` 为准；数据以 `docs/有效性证据.md` 为准；
> 术语以 `README.md` 为准。本章不引用任何未进入仓库的材料。
>
> **状态口径**：文中未标注的均为**已实现并通过测试**的行为；
> 凡是尚未实现的内容，一律单独标注为「后续计划」。

---

## 1. 问题定义：为什么不能把体检报告照片直接丢给通用大模型

最省事的做法是把照片直接发给多模态模型，让它"看看这份报告有什么问题"。
这条路能跑出很像样的回答，因此也最有吸引力。我们不采用，理由有四条，每一条都不是偏好问题。

**第一，读数的错误是静默的。**
视觉模型把 `512` 读成 `512.5`、把升降方向读反，界面上不会有任何告警，输出依旧通顺有条理。
`docs/prompt-log/03-表达层与数字回溯.md` 记下了这个判断：
「VLM 读数的错误是静默的，512 抄成 512.5 没有任何告警，而用户拿到的却是'有 AI 背书'的数字。」

**第二，与用户对不上账。**
模型说"你的尿酸超标 21%"，这个 21% 是它算的，用户没法核对，医生也没法核对，而它读起来非常像真的。
数字一旦来自模型的措辞习惯而非报告原文，后续讨论就失去了共同基准。

**第三，照片里有身份信息。**
体检报告抬头通常包含姓名、性别、年龄、体检号、送检医院与医生。
把整张图发出去，等于把这些信息一并交付给外部服务。对这些字段，我们的选择是**根本不送**（见第 5 节）。

**第四，不可复现。**
同一张图问两次，措辞不同、强调的项可能不同。而这是一个需要"给爸妈看"的产品，
结论必须稳定；一次说"问题不大"、一次说"要尽快复查"，信任就没了。

所以真正的问题不是"要不要用大模型"，而是**把它放在处理链的哪一层**。
`docs/prompt-log/03-表达层与数字回溯.md` 把这次纠偏记为：
「大模型可以进这个产品，但不能进这条位置」。

## 2. 意图边界：四层职责

系统把一个"看懂体检报告"的任务拆成四层。每一层的负责人是固定的，
不是靠模型自觉，而是靠数据结构与调用位置固定下来。

| 层级 | 做什么 | 负责者 | 具体实现 | 大模型能否介入 |
|---|---|---|---|---|
| **识别** | 图 → 文字 → 「指标名 / 数值 / 单位 / 参考区间」四元组 → 归一到标准指标 | 本地 | `app/ocr/engine.py` `extract_text()`；`app/ocr/parser.py` `parse_markers()`；`app/rules/engine.py` `normalize_name()` | **否** |
| **数值判定** | 与参考区间比较得出 偏高 / 偏低 / 在区间内 / 待确认；匹配日常红线 | 本地 | `app/rules/engine.py` `judge()` / `match_redlines()` / `evaluate()`；`app/rules/redlines.json` | **否** |
| **语言表达** | 把已定稿的判定结果写成普通人能看懂的话 | 本地模板（默认）或大模型（可选） | `app/llm/explainer.py` `_template_report()` / `_llm_report()`；`app/llm/chat.py` `QaAnswerer.answer()` | **是**（唯一允许的一层） |
| **日常行动** | 记一餐 → 本地累加 → 对照当前红线 → 今日汇总 / 一周趋势 | 本地 | `app/daily/service.py`；`app/data/db.py` | **否** |

由此得出三条硬约束，都能在代码里找到对应位置：

**约束一：大模型不产生数字。**
送给模型的输入里，每个数字都已由本地确认过（`_facts_json()` 注释写明：
"只送判定结果，不送原始图片、不送未判定的四元组"）。模型写出的数字还要再过一道回溯校验（第 4 节）。

**约束二：大模型不做高低判定。**
`_build_prompt()` 第一句是"数值与高低判定均已由本地系统确定，请你不要修改或重新判断任何数字"。
但这只是提示，不是保障。真正的保障是判定字段（`本地判定`）由本地生成并直接进入输出，
模型只被要求填 `simple_explanation` 与 `recommended_next_step`。

**约束三：大模型不决定红线。**
红线来自 `app/rules/redlines.json` 的 16 条规则，由 `RuleEngine.match_redlines()` 按键
`(marker_id, flag)` 匹配。模型既读不到规则文件，也没有接口能写入红线；
它只是在事实 JSON 里**只读**地看到（`"本地判定": "触发红线「限嘌呤」"`）。

还有一层容易被忽略的约束：**契约里不存在数值型必填字段**。
`app/schemas.py` 的 `LabTest` 中，`reported_value` 是 `str`（须与 OCR 原文逐字一致），
`reference_range` 是可选 `Optional[str]`，其余全是文本或枚举——模型想写数，也只能写在文本里。

## 4. 数字回溯校验的判定方法

校验器是 `app/llm/explainer.py` 里的两个函数：
`allowed_numbers()` 负责"哪些数字有出处"，`find_hallucinations()` 负责"文中的数字是否都能找到出处"。

### 4.1 允许数字的四个来源

`allowed_numbers(analysis)` 收集的集合由四部分组成：

| 来源 | 代码位置 | 例子 |
|---|---|---|
| 报告值（`reported_value` / `value`） | `for j in analysis["judged"]` | 512、5.41 |
| 参考区间的两个端点（`ref`） | 同上，`for bound in j.get("ref")` | 208、428 |
| 小数数值的整数部分 | `if isinstance(v, float) and not v.is_integer()` | 5.41 → 允许 5 |
| 计数（总项数 / 命中数 / 异常数） | `counts` 与顶层 `total/matched/abnormal_count` | 13、4 |

此外还有一张**常识数字白名单** `_BENIGN_NUMBERS`：0–10 的个位数、12/24/30/90/180/365/364 等。
它存在的原因很具体——模型写"建议 3-6 个月后复查""一年 365 天"，这些话没有出处但完全正确，
不放行就会把正确的话判成幻觉（代码注释原话：「若不加这张白名单，'一年 365 天''3-6 个月后复查'都会被误判为幻觉」）。
计数类数字也单独放行，否则报告项数一多（13、22……），本地模板自己写的正确句子会被自己的校验器判死。

### 4.2 三层放行与一条禁止

`find_hallucinations()` 用正则 `\d+(?:\.\d+)?` 切出文中的每个数字，然后依次尝试三种放行：

1. **精确匹配**：token 直接在允许集合里，放行。
2. **尾零归一**：`512.0` 去掉尾零得到 `512`，在集合里则放行。理由是同数不同写法的格式差异。
3. **四舍五入容忍**：**仅当 token 含小数点时**，按 token 的小数位数，把允许集合里的每个值同样舍入后比较。
   于是 `5.41` 被写成 `5.4` 视为措辞，不视为幻觉。

**第四层放行被明确禁止：整数 token 不走四舍五入这条路。**
代码原话是：「'84' 不是 847 的四舍五入，若放行整数前缀，真正的幻觉数字反而会被放过。」

这是校验器最容易写错的地方。一个直观但错误的实现是"token 是某个允许值的前缀即放行"——
那样 `84` 会因为是 `847` 的前缀被放过，而 `847` 恰恰是测试里用来模拟幻觉的编造值。
把容差限制在"小数点位数的舍入"，既不误杀 `5.4`（源自 5.41），也不放过 `84`（无任何出处）。

### 4.3 无出处数字的处理

校验不通过时，`_llm_report()` 的动作序列是固定的：

```
第 1 次输出 → 收集无出处数字 bad → 记 last_err = "第 1 次输出含有无出处数字：[...]"
            → continue，带着这次的事实重新请求（最多 2 次）
第 2 次输出 → 仍然有 bad → 记 last_err
            → 循环结束，last_degraded = DEGRADE_HALLUCINATION
            → 返回 _degraded_report()：本地模板 + 一句如实说明
```

这里有两个细节值得说明。

**其一，"重写"带的是事实，不是惩罚。**
再次请求时 prompt 仍是同一份事实 JSON，模型的输入没有被清理，清理发生在输出侧。
问答链路更进一步：重写提示里会带上违规数字本身
（`tests/test_chat.py` 断言 `"847" in fake.prompts[1]`），让模型知道具体哪个数字多了。

**其二，校验器覆盖的是"散文"，不是结构字段。**
`_llm_report()` 只把 `summary`、每项的 `simple_explanation` 与 `recommended_next_step` 拼起来送校验
（`prose = " ".join(...)`）。结构化字段不走校验器，因为它们**根本不采信模型的值**：
`reported_value` 与 `reference_range` 由本地按指标名回填，`disclaimer` 在 `LabReport.model_validate()` 之前被强制覆盖为本地文案。
代码注释的说法是：「报告值由本地回填，绝不采信模型写的数值」。

同一段还做了两处防御性剔除，都来自实测：模型写出事实里不存在的指标名，以及契约外的顶层字段。
两者按"剔除并记日志"处理，而不是放宽契约——嵌套层仍受 `extra="forbid"` 保护。

## 5. 隐私设计

### 5.1 报告侧的脱敏发生在解析之前

`app/pipeline.py` 的 `Pipeline.analyze()` 顺序是：OCR → **`redact()`** → `parse_markers()`。
脱敏排在解析之前，注释给出的理由值得照录：
「脱敏后的文本会作为上下文送给大模型。若先解析再脱敏，患者信息可能已经混进结构化结果里，反而更容易泄露。」

`redact()` 做两件事：

| 处理 | 规则 | 结果 |
|---|---|---|
| 含身份特征的行 | `_SENSITIVE_LINE` 正则：姓名、性别、年龄、身份证、体检号、病历号、送检与采样时间、病区床号、送检医生、审核者等 | **整行丢弃** |
| 可直接指向个人的编号 | `_REDACT_RULES`：17 位身份证号、`1[3-9]` 开头手机号、10 位以上长数字 | 替换为 `[已抹除]`，并记录字段类型 |

保留指标行是有意的：表达层要看到"尿酸 512，参考 208-428"才写得出人话，
而指标数值本身不构成身份信息。

### 5.2 送给模型的到底是什么

`_facts_json()` 构造的事实 JSON 每项只有七项字段：指标名、报告值、单位、参考区间、本地判定、判定依据、字典解释。
**不含**：姓名、性别、年龄、身份证、体检号、医院名、医生名、原始图片、未判定的四元组。

`tests/test_chat.py` 有直接断言：prompt 不含"姓名段"与"身份证"。

### 5.3 用户提问先脱敏

问答框输入用另一个函数 `mask_pii()`（同在 `app/pipeline.py`）。两者分工写在它的 docstring 里：

- `redact()` 处理整份报告。抬头那一行"姓名 张三 性别 男……"几乎没有与指标有关的信息，整行丢弃是对的。
- `mask_pii()` 处理用户的一句提问。"我今年 45 岁，尿酸 520 要紧吗"整行丢完就什么都不剩，问答直接失效，
  所以只做**定点替换**，保留问题本身。

两者**共用同一张编号正则**（`_REDACT_RULES`）——规则只能有一份，
否则"体检报告脱了、聊天框没脱"这类漏洞迟早出现。

`mask_pii()` 还处理用户自报姓名（`我叫张三`/`姓名：李四`），而刻意不匹配"我是"——
否则"我是尿酸高"会被误伤。这条也有测试：`check("「我是」不误伤", "尿酸高" in clean2, True)`。

## 6. 失败与降级

设计前提是：**模板模式是默认，不是兜底。** 不配置任何 Key，产品的解读、问诊清单、
「给爸妈说的话」、问答、日常层全部可用；配置 Key 之后才升级为大模型改写。

### 6.1 三种失败与各自的处理

异常在 `app/llm/provider.py` 里被分成三类，目的是让后续动作不同：

| 情形 | 判定依据 | 系统动作 | 对用户的表述 |
|---|---|---|---|
| **无 Key** | `Explainer.mode == "template"` | 直接走 `_template_report()`，不发起任何网络请求 | 徽标「本地模板解读」 |
| **模型不可用** | `LLMUnavailable`：缺 Key、鉴权失败、限流、超时、断网、5xx | **不重试**，立刻退模板 | 「AI 暂不可用，已改用本地模板解读，判定结果不受影响」 |
| **输出不合格** | `LLMOutputInvalid`：模型有响应但数字无出处、格式不符 | 带着违规数字**重写一次**；仍不过则退模板 | 「本次大模型输出未通过数字校验，已改用本地模板解读，结论不受影响」 |

第三类"重写一次"的语义已在上节说明；这里强调的是**第二类为什么不重试**。
`LLMUnavailable` 的 docstring 记录了归类的动机：两类混在同一个 `except Exception` 里，
后果是"断网时也会白跑第二次，等待时间翻倍"，以及"退回模板后仍对外声称本次由大模型生成——界面在撒谎"。

超时与重试据此设定（`app/llm/provider.py`）：连接超时 5 秒，读取超时 30 秒，传输层 `MAX_RETRIES = 0`。
不重试的理由是：失败后本来就退本地模板，重试成功也只是把"本地模板"换回"大模型措辞"，不值得让用户多等一遍；
连接问题由 5 秒的连接超时兜住，不会因为读超时给到 30 秒就多等。

`LLMUnavailable` 与 `LLMOutputInvalid` 的异常信息里只放**归类后的一句话原因**，
不放服务商原始报文（里面可能有 request_id、账号片段），原始信息只进日志。

### 6.2 降级之后不谎报

这是本项目在降级链路上最容易出错、也最容易被评委当场戳穿的一点：
**降级之后仍然对外声称"本次由大模型生成"**。

`Explainer.explain()` 的返回值里，`mode` 与 `model` 说的是"这次正文实际由谁生成"，
不是"本来打算由谁生成"：

```python
"mode": "template" if degraded else self.mode,
"model": "本地模板" if degraded else (self.last_model_label or self.model_name),
```

`degraded` 字段取值为 `""` / `unavailable` / `hallucination`，前端据此显示一次性提示并同步顶栏徽标。

### 6.3 降级之后产品还是完整的

`_degraded_report()` 的实现是"先取本地模板报告，再往问诊清单末尾追加一句如实说明"。
也就是说，降级路径与"本来就没有 Key"走的是同一套模板生成逻辑——
逐项解释来自字典的 `explain_high` / `explain_low` 字段，问诊清单来自本地规则，
「给爸妈说的话」由 `family_message()` 生成。

这一点在干净环境里验证过：全新克隆 + 独立 Python 3.11 + 无 `.env`、无任何 Key，
`/api/about` 返回 `explain_mode=template`，全链路走通。

本章每一条技术断言都对应下列测试之一。全部可直接运行，不依赖网络与 API Key。

| 机制 | 测试文件 | 关键断言 | 规模 |
|---|---|---|---|
| 数字回溯的放行与拦截 | `tests/test_llm.py` | `find_hallucinations("你的尿酸是 847…") == ["847"]`；`"512，参考区间 208-428"` 返回 `[]`；常识数字与 `5.4`（源自 5.41）放行 | 33 项 |
| 模板模式完整可用、报告值逐字一致 | `tests/test_llm.py` | 逐项解释覆盖全部指标；`reported_value == "512"`；`disclaimer` 必填 | 同上 |
| 脱敏：提问与报告两侧 | `tests/test_chat.py` | 身份证/手机号/姓名被抹、问题本身保留；报告抬头整行丢弃；prompt **不含**姓名段与身份证 | 53 项 |
| 编数字 → 重写一次 → 仍不过退模板 | `tests/test_chat.py` | `attempts == 2`、违规数字出现在重写提示里；未知食物返回空列表；答案中不出现 `120/80` | 同上 |
| 未知指标不猜、定性项判定 | `tests/test_rules.py` | 未收录指标 `normalize_name()` 返回 `None`；`"阴性（-）"` 判 `normal`；无法识别判 `unknown` | 54 项 |
| 三类失败分别降级且归类正确 | `tests/test_degrade.py` | 401 / 429 / 超时 / 断网 / 5xx / 编数字 各走各的分支；降级后 `mode` 变 `template` | 134 项 |
| 16 条红线逐条可触发 | `tests/redline_bench.py` | 16 条阳性 + 11 条阴性/边界，预期与实际逐项对照 | 27 条用例 / 293 项 |
| 端到端（图 → OCR → 判定 → 红线） | `tests/test_e2e.py` | 12 份合成样本，识别 106 行全部命中 | 177 项 |

运行方式：

```bash
python tests/test_llm.py        # 表达层与数字回溯
python tests/test_chat.py       # 问答、隐私、重写与降级
python tests/test_rules.py      # 字典归一与本地判定
python tests/test_degrade.py    # 三类失败的降级链路
python tests/redline_bench.py   # 红线规则逐条对照（退出码 0/1）
python tests/test_e2e.py        # 端到端
```

其中 `tests/redline_bench.py` 的退出码有语义：0 表示全部一致，1 表示存在不一致。
它做过负控验证——故意把一条用例的预期改错后，退出码变为 1，并同时报出"用例自查失败"与"对照失败"。

`tests/test_llm.py` 的设计值得单独提一句：它用**故意编造的假数据**驱动校验器，
而不是只用真实数据跑一遍。只用真实数据测等于没测——必须证明它抓得住幻觉，
否则"校验通过"可能只是"校验器什么都没查"。

## 8. 诚实边界

**不做诊断，不推荐药物。**
`app/llm/explainer.py` 的 `DISCLAIMER` 写明"本内容不构成医疗建议，请遵医嘱，
数值来自报告本身，判定基于公开的成人参考区间"。它是 `LabReport` 的结构体必填字段，
在 `LabReport.model_validate()` 之前被强制注入为本地文案，不接受模型改写；Prompt 里也写明"不诊断、不建议用药"。

**OCR 仍可能读错。**
实测口径是：8 张公开真实报告图共解析 66 行指标、61 行命中字典，字典命中率 92%，命中行判定可用率 100%。
这个数字说的是"解析出的行里能归一到字典的比例"，
**不表示识别出的每个字符都正确，也不表示系统整体结论的正确率**。
最差的一份只解析出 2 行；尿检/乙肝版式解析 5 行仅命中 1 行，这类版式的定性解析路径尚未验证。

**未知指标如实标为待确认，不让模型猜。**
字典（`app/dict/markers.json`，当前 80 条）认不出的指标不进入判定，归入 `unmatched`；
认出来但缺参考区间或数值无法解析的，判定为 `unknown`，文案层统一显示"待确认"（`_flag_word()` 的映射）。
宁可少判一项，也不拿最像的那一项硬套。

**规则覆盖是有限的。**
红线规则当前 16 条，覆盖嘌呤、糖、钠、脂肪、铁、酒精、蛋白七类日常约束，不是全部指标异常。
甲状腺相关指标刻意不做饮食映射，转为问诊提示——碘的边界容易踩雷。

**参考区间是成人通用值。**
不支持儿童、孕期等特殊人群；以报告上印刷的区间为准。

**血压阈值来自指南，不是本项目实测的结论。**
`app/daily/service.py` 的 `BP_THRESHOLD = (140, 90)` 取自诊室标准。
它定义在服务层而非报告字典——因为血压是测量值，报告上不会有这一项。

**后续计划（尚未实现，不构成本章结论）**：
尿检/乙肝版式的定性解析验证；字典扩充至约 120 条；家人档案与成员切换界面；
手动校正入口（OCR 失败时的兜底界面，当前没有）。

## 9. 评委问答：为什么不直接拍照问 AI 就够了

**问：既然现在的多模态模型已经能看图，为什么不直接拍照上传、让它直接回答？**

答：因为这条路径交付的是"一段很像答案的文字"，而我们交付的是"一条可以对账的链路"。
具体差在三点。

**第一，数字可信。**
直接问 AI，数字由模型生成：它可能读错、可能算错、也可能为了让回答完整而补一个不存在的值，
这三者在界面上无法区分。本项目把数字的产生与语言的产生切开——指标值来自 OCR 与报告原文，
高低判定来自 `app/rules/engine.py` 与字典区间，红线来自 `app/rules/redlines.json`。
模型只被允许改写措辞，写出的每个数字还要过 `find_hallucinations()` 回溯校验；
对不上就重写一次，仍对不上就退本地模板。所以最终给出的每一个数字，都能指回报告上的某个位置。

**第二，隐私。**
体检报告抬头是姓名、体检号、医院与医生，直接拍照提问意味着这些信息一并离开本机。
本项目的处理是：`redact()` 在解析之前整行丢弃含身份特征的行，编号类替换为 `[已抹除]`，
送给模型的只有指标名、报告值、单位、参考区间、判定与字典解释这几类字段；用户提问也先过 `mask_pii()`。
判定与红线全部本地计算，不依赖外部服务。

**第三，持续陪伴。**
"这份报告有什么问题"是一次性问答；这个产品要回答的是"接下来 364 天该怎么吃"。
报告定义红线 → 每天记一餐 → 本地累加后对照红线 → 今日提示与一周趋势，全部在本地完成。
所以无 Key、断网、限流三种情况下，产品依旧给出完整的解读与日常对照。

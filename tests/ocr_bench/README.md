# OCR 选型评测（Day 3-5）

## 为什么要先做这个

OCR 是本项目唯一的**不可绕过的技术风险**。报告上的数字抽不准，后面所有功能——
红线、日常对照、周报——全都建立在错误之上。

所以不猜哪家好用，**用数据选**。

评测分两层：

| 层 | 评什么 | 为什么要有这层 |
|---|---|---|
| **L1 文本层** | OCR 吐出的原始文字对不对 | OCR 的基本功 |
| **L2 字段层** | 能不能抽出「指标名 / 数值 / 单位 / 参考区间」四元组 | 这才是我们真正要的 |

> L2 的关键是：**三家 provider 共用同一个解析器**。
> 如果每家配专属解析器，比的就是"我给谁写的解析器更好"，而不是"谁的 OCR 更强"。

---

## 方案选择：先合成，再补真实件

网上能找到的中文体检报告数据集，**没有一个同时满足「免费 + 可商用 + 已脱敏」**：

| 数据集 | 规模 | License | 问题 |
|---|---|---|---|
| 数据堂 6087 张体检报告 | 6087 中文 | 商用付费 | 要钱 |
| 天池 / 启智 中文化验单 | 238 中文 | CC-BY-**NC** | 非商业许可，且是真实单据 |
| ClinOCR-Bench | 384 | MIT | 合规但**英文** |
| MedOCR-Vision | 2462 | MIT | 英文 |

所以采用两步走：

| 步骤 | 数据来源 | 作用 |
|---|---|---|
| 1 | **合成报告**（`synth.py` 生成） | 跑通流程、横向对比各 OCR 引擎的相对强弱 |
| 2 | **1-2 份真实脱敏报告** | 最终确认——合成件再逼真也代表不了真实纸张 |

### 生成合成样本

```bash
python synth.py --count 12 --degraded 4 --clean
```

产出 12 份：**4 种排版 × 3**（有框线表格 / 无线表 / 双栏 / 带机构抬头），
其中 4 份做了**拍照退化**（旋转 ±4°、高斯模糊、椒盐噪点、单侧明暗不均）。

合成样本的 ground-truth 是 **100% 精确**的——图是我们画的，答案就是写进去的那些数。
但它**不能替代真实样本**：真实纸张的折痕、反光、印章遮挡、装订孔，模拟不出来。

---

## 第一步：准备样本（需要你来做）

### 1.1 收集

目标 **10-15 份**真实体检报告，尽量覆盖不同来源：

- 医院打印的纸质报告（手机拍照）
- PDF 电子版
- 不同排版（单栏 / 双栏 / 表格线密集 / 无线表）
- 不同医院（排版风格差异很大）

至少包含 **2 份拍照件**——拍照有倾斜和阴影，是最差情况，必须测。

### 1.2 脱敏（⚠️ 这一步不能省）

**任何样本放进 `samples/` 之前，必须抹掉：**

- 姓名
- 身份证号
- 体检号 / 病历号
- 医院名称
- 医生姓名
- 二维码 / 条形码（可能编码了身份信息）

用画图工具涂黑即可，或者只截取「检验结果表格」那一段。

> `samples/` 已被 `.gitignore` 排除，不会进 Public 仓库。
> 但这不代表可以不脱敏——**本地泄密同样是泄密**。

### 1.3 放入

```
tests/ocr_bench/samples/
  ├── 001.jpg
  ├── 002.pdf
  └── ...
```

命名随意，但**每份样本要在 `expected/` 里有同名 `.json` 标注**。

## 第二步：人工标注（需要你来做）

在 `expected/` 下建同名文件，例如 `001.jpg` 对应 `expected/001.json`：

```json
{
  "source": "拍照件，单栏无线表",
  "markers": [
    { "name": "尿酸",     "value": "512", "unit": "μmol/L", "ref": "208-428" },
    { "name": "血红蛋白", "value": "135", "unit": "g/L",    "ref": "130-175" },
    { "name": "甘油三酯", "value": "2.8", "unit": "mmol/L", "ref": "0.45-1.70" }
  ]
}
```

规则：

- **只标注指标数值，绝对不要抄姓名、体检号、医院**
- 每份挑 **10-20 个指标**就够，不用全标
- `ref` 就照报告上印的写（有的报告写成"208~428"也可以）
- 标注就是你自己的眼睛，是评判 OCR 的唯一标准，请照着报告逐字抄

> 标注 10-15 份大概要花 1-2 小时。这 1-2 小时能避免后面选错 OCR 返工一周。

## 第四步：怎么选

不要只看总分，看**最弱的那一项**：

| 情况 | 结论 |
|---|---|
| 四项都在 90% 以上 | 直接用，留 2 天缓冲 |
| `ref`（参考区间）明显偏低 | 危险——区间判错，红线就判错。换一家 |
| 拍照件比扫描件低 20 个点以上 | 需要在前端加"请正对拍摄"的引导 |
| 全部低于 85% | 别硬扛，考虑**手动校正界面**作为兜底（这本身是加分项） |

> 一个容易被忽略的点：**参考区间比数值更重要**。
> 数值错一点还能靠字典兜底，区间错了整套判定就歪了。

## 当前基线结论（RapidOCR，12 份合成样本）

```bash
python bench.py --provider rapidocr
```

| 维度 | 结果 | 说明 |
|---|---|---|
| **单栏样本（9 份）平均** | name 82% · value 82% · unit 55% · **ref 81%** | 排除双栏后 |
| 有框线表格（boxed） | 91% ~ 100% | 最好，也是真实报告的主流排版 |
| 无线表（noline） | 83% ~ 90% | 尚可 |
| 带抬头（header） | 清晰 83-85%，**退化件仅 25%** | 对拍照质量最敏感 |
| 双栏（twocol） | 不适用 | **已知限制**，见下 |

### 三条选型判断

1. **`ref`（参考区间）81% 是决定性指标**——区间能读准，红线判定就可靠。
   这一项达标，RapidOCR 可以作为基线方案。

2. **`unit` 只有 55%，但不致命。** 失败集中在**上标单位**：
   `×10⁹/L` 被认成 `×10°/L`、`×10¹²/L` 被认成 `×101/L`，
   以及 `μmol/L` 的字母 l 被认成数字 1。
   而单位本来就在指标字典里（Day 6-9），OCR 读错可由字典兜底。
   → 字典里要为这些误识别形态登记别名。

3. **拍照退化件的风险必须正视。** 最差的样本（带抬头 + 退化）跌到 25%。
   → 产品对策：前端加"请正对拍摄、避免阴影和反光"的引导，
     并提供**手动校正入口**（这本身也是赛题加分项）。

### 下一步

申请百度 OCR 后跑 `--provider all` 做横向对比。
重点看：云端引擎对**退化件**是否明显强于本地引擎——
如果强很多，说明拍照鲁棒性值得额外投入；如果差不多，本地方案就够了。

## 环境准备

**PaddleOCR**（本地，零门槛但安装重）：

```bash
D:/aconda3/envs/hwh_ml/python.exe -m pip install paddlepaddle paddleocr
```

**百度 OCR**（需要申请，但有免费额度）：

1. 去 ai.baidu.com 注册 → 创建应用 → 勾"通用文字识别（高精度版）"
2. 拿 `AppID` / `API Key` / `Secret Key` 填进 `.env`

> **建议现在就去申请百度**——实名认证可能要等 1-2 天，
> 这个等待不占用你的开发时间，但会卡住对比评测。
> 申请期间可以先用 PaddleOCR 跑出本地基线。
